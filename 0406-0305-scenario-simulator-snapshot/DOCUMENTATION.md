# Scenario Simulator — Product & Technical Documentation

This document is the single source of truth for what the product is, how it
works, and how to rebuild it from scratch. It is written so that a future
developer (or AI agent) can recreate the application end-to-end without
relying on the existing codebase.

For a more focused breakdown see also:

- [`docs/architecture.md`](docs/architecture.md) — system architecture and

- [`docs/api.md`](docs/api.md) — every HTTP endpoint and SSE event.

- [`docs/rebuild-from-scratch.md`](docs/rebuild-from-scratch.md) — ordered,
  step-by-step guide to recreate the app.

## 1. Product overview

**Scenario Simulator** is a facilitated, multi-team training platform.
A facilitator runs a *workshop* in which several teams of four participants
each work through the same business *scenario* in parallel. The current
scenario, *"The Demand Spike"*, asks teams to investigate a fictional
beverage company's supply-chain crisis and define the **right problem to
solve** — not solve it.

There are three audiences in the app:

1. **Participants** — join a workshop with a code, pick a team name, and
   walk through the scenario screen by screen.
2. **Moderator / facilitator** — watches every team in real time, sends
   notes, asks for screen access, and flags teams for debrief.
3. **Results / debrief view** — a read-only summary used after the
   workshop to compare team submissions side by side.

### Core flow per team

```
Brief → Stakeholders → Interview → Evidence → Define Problem → Submit
```

Six logical steps (the simulation has more sub-screens but the moderator
dashboard rolls them up into these six). Each team has exactly one live
session per workshop, identified by `(workshopId, teamName)`.

### Live experience

Both participant and moderator views update in real time without polling
through a single Server-Sent Events (SSE) stream at `/api/events`. The
client uses these events to invalidate the relevant React Query caches,
which then refetch the affected resource.

## 2. Tech stack

| Layer            | Technology |
| ---------------- | ---------- |
| Monorepo         | pnpm workspaces |
| Language         | TypeScript 5.9 (strict) |
| Runtime          | Node.js 24 |
| Frontend         | React 19 + Vite 7 + Tailwind CSS 4 + Radix UI primitives |
| Routing (web)    | wouter |
| Data fetching    | @tanstack/react-query (hooks generated by Orval from OpenAPI) |
| Backend          | Express 5 |
| Database         | PostgreSQL 16 + Drizzle ORM |
| Validation       | Zod (`zod/v4`), `drizzle-zod` |
| API contract     | OpenAPI 3.1 → Orval codegen → React Query hooks + Zod schemas |
| Live updates     | Server-Sent Events (native EventSource, no extra deps) |

| Hosting          | Replit Autoscale Deployment via path-based reverse proxy |

There is no auth — workshops are unlisted, identified by a short code that
the facilitator shares (e.g. `ABCD`).

```

│   ├── api-server/             Express + Drizzle backend (kind: api,  base: /api)
│   ├── scenario-simulator/     React + Vite frontend     (kind: web,  base: /)
│   └── mockup-sandbox/         Internal canvas/preview   (kind: design, base: /__mockup)
├── lib/
│   ├── api-spec/               openapi.yaml + orval.config.ts (single source of truth)
│   ├── api-client-react/       Generated React Query hooks (do not hand-edit)
│   ├── api-zod/                Generated Zod schemas (do not hand-edit)
│   └── db/                     Drizzle schema + pg pool + drizzle-kit config
├── scripts/
│   ├── post-merge.sh           Runs after each task merge (DB push, etc.)
│   └── src/                    Shared TS scripts (snapshot, etc.)
├── pnpm-workspace.yaml         Workspace globs, catalog pins, esbuild overrides
├── tsconfig.base.json          Strict shared TS defaults
├── tsconfig.json               Solution file for composite libs
└── package.json                Root: typecheck / build orchestration
```

Rules of the monorepo (enforced socially, not mechanically):

- `artifacts/*` and `scripts` are **leaf** packages — checked with
  `tsc --noEmit`, never depended on by other packages.
- `lib/*` are **composite** — emit declarations via `tsc --build`, are the
  only place to share code between artifacts.
- Every package owns its own `package.json` dependencies. Versions that are
  shared come from the `catalog:` in `pnpm-workspace.yaml`.

## 4. Artifacts

The repo currently has three artifacts. Each one is a self-contained
deployable unit declared by its own `.replit-artifact/artifact.toml`.

### `artifacts/api-server` (kind: `api`, base path: `/api`)

Express 5 server. Boots in `src/index.ts`, mounts the router from
`src/routes/index.ts` under `/api`. Listens on `process.env.PORT`.

On startup it runs `bootstrapDatabase()` (idempotent SQL in
`src/lib/bootstrap.ts`) which:

1. Creates the `workshops` table if missing and inserts a `DEFAULT`
   workshop row.
2. Adds the `workshop_id` column to `sessions` (nullable), backfills it
   to the default workshop, then makes it `NOT NULL`.
3. Drops the legacy global `team_name` unique constraint and adds the
   composite `(workshop_id, team_name)` unique.

Production build is a single bundled CJS file at
`artifacts/api-server/dist/index.mjs` produced by `esbuild` (see
`build.mjs`).

### `artifacts/scenario-simulator` (kind: `web`, base path: `/`)

React 19 SPA bundled by Vite. `src/main.tsx` mounts `<App />` from
`src/App.tsx`, which sets up:

- `QueryClientProvider` (TanStack Query)
- `TooltipProvider`, `Toaster` (Radix-based UI primitives)
- `wouter` routing under `import.meta.env.BASE_URL`

Routes:

| Path                          | Page component               | Purpose |
| ----------------------------- | ---------------------------- | ------- |
| `/`                           | `LandingScreen`              | Pick or create a workshop |
| `/w/:code`                    | `EntryScreen`                | Enter team name; create or resume session |
| `/play/:sessionId/:screen`    | `SimulationApp`              | The participant simulation flow |
| `/results/:code`              | `FacilitatorDashboard`       | Read-only post-workshop comparison |
| `/moderator/:code`            | `ModeratorDashboard`         | Live moderator dashboard |
| _otherwise_                   | `NotFound`                   | 404 |

The participant simulation is implemented as a screen state machine in
`src/simulation/SimulationApp.tsx` driven by the `currentScreen` field on
the session row (`company`, `stakeholder`, `interview`, `evidence`,
`define`, `submit`, `complete`). Each `PATCH /sessions/:id` writes the new
screen + any chosen field; the moderator sees the change live.

### `artifacts/mockup-sandbox` (kind: `design`, base path: `/__mockup`)

Internal Vite preview server used by the canvas / mockup workflow. Not
part of the shipped product.

### Routing

A global reverse proxy maps base paths to artifacts (configured in each
artifact's `artifact.toml`). Most-specific path wins, so `/api` does not
collide with `/`. Frontend code never hardcodes ports.

## 5. Domain model (database)

Three tables, all in `lib/db/src/schema/`.

### `workshops`

| Column      | Type        | Notes |
| ----------- | ----------- | ----- |
| `id`        | `uuid` PK   | `gen_random_uuid()` |
| `code`      | `text` UNIQUE | The shareable join code (e.g. `ABCD`) |
| `label`     | `text`      | Human label shown in UI |
| `created_at`| `timestamptz` | `default now()` |

A `DEFAULT` workshop is seeded by the bootstrap so existing sessions
always have a parent.

### `sessions` — one per (workshop, team)

| Column                     | Type        | Notes |
| -------------------------- | ----------- | ----- |
| `id`                       | `uuid` PK   | |
| `workshop_id`              | `uuid` FK → workshops.id (cascade) | |
| `team_name`                | `text`      | UNIQUE with `workshop_id` |
| `current_screen`           | `text`      | default `"company"` |
| `selected_stakeholder`     | `text` nullable | |
| `selected_evidence_source` | `text` nullable | |
| `answers`                  | `jsonb` `AnswerRecord[]` | `{ questionId, selected: A|B|C }` |
| `problem_statement`        | `text`      | default `""` |
| `confidence`               | `text` enum `Low|Medium|High` nullable | |
| `assumption`               | `text`      | default `""` |
| `flagged_for_debrief`      | `boolean`   | default `false` |
| `submitted_at`             | `timestamptz` nullable | Set by `POST /sessions/:id/submit` |
| `created_at` / `updated_at`| `timestamptz` | `updated_at` is bumped on every PATCH |

### `moderator_notes`

| Column         | Type        | Notes |
| -------------- | ----------- | ----- |
| `id`           | `uuid` PK   | |
| `session_id`   | `uuid` FK → sessions.id (cascade) | |
| `message`      | `text`      | Body shown to participants |
| `template_id`  | `text` nullable | Optional preset id |
| `created_at`   | `timestamptz` | |
| `dismissed_at` | `timestamptz` nullable | Set when participant dismisses the note |

### `access_requests`

| Column         | Type        | Notes |
| -------------- | ----------- | ----- |
| `id`           | `uuid` PK   | |
| `session_id`   | `uuid` FK → sessions.id (cascade) | |
| `status`       | `text` enum `pending|granted|declined` | default `pending` |
| `created_at`   | `timestamptz` | |
| `responded_at` | `timestamptz` nullable | |

A **partial unique index** `access_requests_pending_per_session` on
`session_id WHERE status = 'pending'` enforces at most one pending
request per session at the database level. The `POST` endpoint uses
`INSERT … ON CONFLICT DO NOTHING` and then re-fetches, returning the
existing pending request idempotently.

## 6. API surface (contract-first)

The single source of truth is **`lib/api-spec/openapi.yaml`**. Every other
API artifact in the repo is generated from it:

| Generated package             | Purpose |
| ----------------------------- | ------- |
| `@workspace/api-client-react` | React Query hooks (`useFoo`, `getFooQueryKey`) used by the frontend |
| `@workspace/api-zod`          | Zod schemas used by the server to validate request bodies / params |

Regenerate after any spec change:

```sh
pnpm --filter @workspace/api-spec run codegen
```

Endpoints (all under `/api`, see `docs/api.md` for full request/response
shapes):

| Method | Path                                         | Operation |
| ------ | -------------------------------------------- | --------- |
| GET    | `/healthz`                                   | `healthCheck` |
| GET    | `/workshops`                                 | `listWorkshops` |
| POST   | `/workshops`                                 | `createWorkshop` |
| GET    | `/workshops/{code}`                          | `getWorkshop` |
| GET    | `/sessions`                                  | `listSessions` |
| POST   | `/sessions`                                  | `createOrResumeSession` |
| GET    | `/sessions/{id}`                             | `getSession` |
| PATCH  | `/sessions/{id}`                             | `updateSession` |
| DELETE | `/sessions/{id}`                             | `deleteSession` |
| POST   | `/sessions/{id}/reset`                       | `resetSession` |
| POST   | `/sessions/{id}/submit`                      | `submitSession` |
| GET    | `/submissions`                               | `listSubmissions` |
| POST   | `/sessions/{id}/flag`                        | `setSessionFlag` |
| GET    | `/sessions/{id}/notes`                       | `listSessionNotes` |
| POST   | `/sessions/{id}/notes`                       | `createSessionNote` |
| POST   | `/notes/broadcast`                           | `broadcastNote` |
| POST   | `/notes/{id}/dismiss`                        | `dismissNote` |
| GET    | `/sessions/{id}/access-requests`             | `listSessionAccessRequests` |
| POST   | `/sessions/{id}/access-requests`             | `createSessionAccessRequest` (dedupes pending) |
| POST   | `/access-requests/{id}/respond`              | `respondAccessRequest` |
| GET    | `/events?workshopCode=ABCD`                  | SSE stream (see below) |

### Live updates (SSE)

`GET /api/events` opens a `text/event-stream` and emits the following
event types (all carry `sessionId`, `at`, and where applicable
`workshopId` + `workshopCode` so the client can scope by workshop):

- `submission.created`, `submission.updated`, `submission.deleted`
- `note.created`, `note.dismissed`
- `flag.changed`
- `access.requested`, `access.responded`

Heartbeat comments (`: heartbeat <ts>`) are written every 25 s. The
client filters by `workshopCode` query param to avoid cross-workshop
chatter.

The frontend uses these events to call `queryClient.invalidateQueries`
on the relevant query keys (e.g. an `access.requested` event invalidates
`getListSessionAccessRequestsQueryKey(sessionId)`). React Query then
refetches and the UI updates within ~1 s of the server change.

## 7. Frontend architecture

### Pages

- **`landing.tsx`** — lists workshops via `useListWorkshops`, lets the
  facilitator create a new one (`useCreateWorkshop`) or join an existing
  code.
- **`entry.tsx`** — validates the workshop code, prompts for a team name,
  calls `useCreateOrResumeSession` and routes to `/play/:id/:screen`.
- **`simulation/SimulationApp.tsx`** — the participant flow. Reads the
  session, advances `current_screen` via `PATCH /sessions/:id`, and
  finally posts `/sessions/:id/submit` which writes `submitted_at` and
  emits `submission.created`.
- **`pages/moderator.tsx`** — the moderator dashboard. The largest
  surface in the app (~2 kLOC). Subscribes to `/api/events` for the
  workshop, groups teams by status (Attention → Slow → On track →
  Complete → Not started), shows a per-team progress bar and
  human-readable "time on step", lets the moderator send notes / flag /
  request screen access, and surfaces a polished activity ticker with
  per-event icons, relative timestamps, and chip filters
  (incl. "Submissions only").
- **`pages/results.tsx`** — read-only debrief view that lists every
  submitted team's problem statement, evidence and assumptions side by
  side.

### Shared static content

`src/data/data.ts` and `src/data/moderatorData.ts` contain product
copy and types that are *not* server-driven (company narrative,
stakeholder names, note templates, status enums). The server only stores
participant-generated data; the scenario itself is shipped with the
client bundle.

### Styling

- Tailwind CSS 4 via `@tailwindcss/vite`.
- A dark navy/purple palette with a yellow CTA accent. Background
  gradients are hand-tuned for the moderator and entry screens.
- Radix UI primitives wrapped in `src/components/ui/*` for things like
  Dialog, Tooltip, Toast.

### State management

There is no global store. Server state lives in React Query; transient
UI state lives in component state. SSE events drive cache invalidation,
not direct state mutation, so the cache stays the single source of
truth.

## 8. Backend architecture

`artifacts/api-server/src/`:

- `index.ts` — reads `PORT`, runs `bootstrapDatabase()`, then `app.listen`.
- `app.ts` — Express app: pino-http logger, CORS, JSON body parser,
  mounts router under `/api`.
- `routes/index.ts` — mounts `health`, `workshops`, `sessions`, `events`,
  `moderator` sub-routers.
- `routes/sessions.ts` — sessions CRUD, reset, submit, flag.
- `routes/moderator.ts` — notes (per-session + broadcast + dismiss) and
  access requests (with pending dedupe).
- `routes/events.ts` — SSE stream with workshop scoping and heartbeats.
- `lib/events.ts` — `submissionsBus` (Node `EventEmitter`) used by
  routes to publish `AppEvent`s consumed by the SSE handler.
- `lib/bootstrap.ts` — idempotent SQL bootstrap (see §4).
- `lib/logger.ts` — pino logger singleton.

Conventions:

- **Never use `console.log` in server code.** Use `req.log` inside route
  handlers and the singleton `logger` in non-request code.
- **Validate inputs with Zod** (the schemas come from
  `@workspace/api-zod`). Inputs that don't validate get a `400`.
- **Emit an event for every mutation** that the moderator dashboard
  cares about, via `submissionsBus.emitSubmission({ … })`.

## 9. Build, run, and deploy

### Local commands

| Command | Purpose |
| ------- | ------- |
| `pnpm install` | Install everything (root + workspaces) |
| `pnpm --filter @workspace/api-spec run codegen` | Regenerate hooks + Zod schemas from OpenAPI |
| `pnpm --filter @workspace/db run push` | Push Drizzle schema to the configured `DATABASE_URL` |
| `pnpm run typecheck` | Build composite libs, then `tsc --noEmit` for every leaf |
| `pnpm run build` | Typecheck + build all artifacts |

Do **not** run `pnpm dev` at the workspace root. Each artifact runs
through a Replit workflow that injects `PORT` and `BASE_PATH`.

### Workflows (Replit)

| Workflow | Command |
| -------- | ------- |
| `artifacts/api-server: API Server` | `pnpm --filter @workspace/api-server run dev` |
| `artifacts/scenario-simulator: web` | `pnpm --filter @workspace/scenario-simulator run dev` |
| `artifacts/mockup-sandbox: Component Preview Server` | `pnpm --filter @workspace/mockup-sandbox run dev` |

### Environment variables

| Var | Where | Notes |
| --- | ----- | ----- |
| `DATABASE_URL` | api-server, db push | Postgres connection string. Required. |
| `PORT`         | every service | Injected by the workflow / artifact config. Required by the api-server entry. |
| `NODE_ENV`     | api-server | Set to `production` in production builds. |
| `BASE_PATH`    | web artifacts | Injected so Vite can serve under a non-root prefix. |

There are **no third-party API keys** required for the product itself.

### Production deployment (Replit Autoscale)

`/.replit` declares Autoscale deployment with `router = "application"`.
Each artifact's `artifact.toml` describes its build + run commands and
the path it serves. The api-server's `artifact.toml` defines a startup
health probe at `/api/healthz`. The scenario-simulator artifact builds
to `dist/public` and is served as static files with a SPA rewrite
(`/* → /index.html`).

After each task merge, `scripts/post-merge.sh` runs (timeout 20 s)
and applies any pending `drizzle-kit push` — see `references/db.md`.

## 10. Snapshot / "downloadable copy" of the app

Two ways to take an offline copy of the project for later recreation:

1. **Replit "Download as ZIP"** — three-dot menu in the file tree.
   Includes everything in the repo (including this documentation) but
   excludes the database. You can re-import it into Replit later, or
   run it anywhere with Node 24, pnpm, and a Postgres database.

2. **`pnpm --filter @workspace/scripts run snapshot`** — the
   `scripts/src/snapshot.ts` utility produces
   `dist/scenario-simulator-snapshot.tar.gz` (~4 MB) containing the
   source tree, the OpenAPI spec, the Drizzle schema, the documentation
   pack, and a pinned `pnpm-lock.yaml`. It deliberately excludes
   `node_modules`, build outputs, `.git`, `.local`, and any `.env*`
   files so the archive stays small and safe to share.

To recreate the running app from a fresh clone of either snapshot:

```sh
pnpm install
# Provide a Postgres URL
export DATABASE_URL="postgres://…"
pnpm --filter @workspace/db run push
pnpm --filter @workspace/api-spec run codegen
pnpm run build
# then run the api-server and the scenario-simulator dev servers
```

See `docs/rebuild-from-scratch.md` for the long version.
